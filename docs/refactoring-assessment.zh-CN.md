# ComicViewer 重构评估

评估日期：2026-09-20。基线提交：`b0761ca`。本轮只评估与验证，没有修改业务代码。

## 结论

可以重构，且有明确收益空间。优先目标应是减少重复调度、明确内存所有权和异步任务生命周期，再简化类的职责。当前规模适合在原项目中分阶段调整，保留 WPF、SharpCompress 和 mpv 的现有实现基础。

最值得先处理的三个方向：

1. 按阅读会话隔离缓存、请求和取消状态，避免旧任务修改新任务的数据。
2. 把全书反复排序、扫描改成围绕可见页面的增量调度。
3. 为视频源和缓存建立一致的持有、计费、释放规则。

不把减少文件数或引入完整 MVVM 框架作为目标。仅拆开 partial 文件不会减少耦合；单纯减少代码行数也不能保证性能收益。

## 优先处理的问题

### 1. 高优先级：旧请求能修改新会话的加载状态

位置：`MainWindow.Media.cs:207`、`:258`、`:292`、`:418`、`:444`、`:580`。

`AcceptImage/AcceptVideo` 能识别旧 generation，但随后调用的 `FinishStaleRequest` 没有 generation 或请求身份判断。它直接按 EntryKey 删除 `_loadsInFlight`，并扣减当前 `_reservedCacheBytes`。停止加载时，这些字段又会被清空并供新会话复用。

例如旧包和新包都有 `0.jpg`：新包已经登记该页的加载请求，旧包延迟到达的回调仍可删掉它的标记，扣掉新包的预算。图片解码回调也在检查 generation 之前删除 `_decodesInFlight` 的同名条目。

局部验证：把窗口状态设为 generation 2，为新请求登记 `0.jpg` 和 64 MiB 预留，再调用旧请求的 `FinishStaleRequest`。结果是新标记被删除、预留变为 0。这个验证构造了交错状态，未测量真实切包时的发生频率。

建议：每次打开压缩包创建独立 ReaderSession，持有自己的 ArchiveSession、缓存和任务状态；每个请求带会话身份与唯一请求身份。旧请求只释放其所属会话的资源。载入方法显式接收会话，不在后台任务中重新读取窗口的 `_archiveSession`。

### 2. 高优先级：缓存预算不覆盖实际持有量，视频停止后仍被保留

位置：`MainWindow.Media.cs:193`、`:216`、`:231`、`:301`；`MainWindow.Video.cs:100`、`:445`；`MpvVideoPlayerControl.xaml.cs:15`、`:171`、`:400`、`:499`；`VideoThumbnailService.cs:167`、`:220`。

确认的问题：

- 准入只检查“当前缓存 + 已预留”是否达到 512 MiB，没有把本次请求大小加进去。
- 当前页和已实现容器可以绕过上述判断；因此该值不是严格峰值限制。
- 缓存统计主要计算编码图片、完整视频和编码封面，不计算解码位图、mpv/GPU 缓冲。保留 ArraySegment 时，数组容量大于 Count 的部分也可能未计入。
- 用户点击未缓存视频时，会单独读取整段视频，没有加入统一的预留/去重流程；可能与后台预加载重复读取同一条目。
- 播放器 `Stop()` 不清空控件的 `_source` 或引擎的 `_videoData`。
- 封面会话 `Stop()` 清空 URI，却不清空 `_currentVideoData`。即使缓存被清理，长期存在的服务仍持有最后处理的视频。
- 封面写回增加 `_cacheBytes` 后，没有立即执行预算淘汰。

局部验证：缓存设置为 500 MiB，下一个非当前页请求为 64 MiB，实际被接收；缓存加预留达到 564 MiB。

建议：明确“编码缓存预算”“解码位图预算”和“活动视频持有量”；分配前检查本次申请，淘汰后再预留；播放和预加载复用同一条目请求。区分可恢复的 Pause 与释放媒体源的 Stop/Unload，在原生流安全关闭后解除托管数据引用。保留播放器实例不应意味着保留上一本书的视频数据。

当前 UI 明确表达纯内存播放、不写临时文件。重构首先保留这一行为。是否支持大视频临时文件或其他可寻址数据源，属于后续功能取舍，不能在整理代码时顺带改变。

### 3. 高优先级：每次选取待加载页都会重新排序全书

位置：`MainWindow.Media.cs:42`、`:151`、`:166`；`MainWindow.Navigation.cs:319`。

`CreateNextMediaRequest` 每取一个请求，就调用 `EnumeratePagesFrom` 对全部页号执行 `OrderBy/ThenBy`，然后从排序结果开头扫描已经缓存或正在加载的条目。这个过程通过 Dispatcher 在 UI 线程执行，并会对已有缓存重复调用 `ApplyCachedMedia`。

固定阅读位置、连续选取 N 页时，仅重复排序部分就可能累计到 O(N² log N)，已加载前缀扫描也会持续增长。

独立微基准结果：

| 页数 | 累计选取耗时 | 当前线程累计分配 |
| ---: | ---: | ---: |
| 500 | 47.6 ms | 5.1 MiB |
| 2,000 | 545.6 ms | 77.6 MiB |
| 5,000 | 2,099.7 ms | 479.9 MiB |

方法：Release/net8.0-windows，固定当前位置为页数的三分之一；每次调用应用实际的 `EnumeratePagesFrom`，通过 foreach 跳过已选前缀后取下一项。计时包含反射调用和枚举，不包含解压、解码、Dispatcher、页面更新或渲染。每档只测一次，数据用于确认规模增长；累计分配不是同时驻留内存，2.1 秒也不是某一次 UI 卡顿时长。实际缓存能否容纳这么多页取决于素材大小。

建议：直接按前后页偏好产生索引，或在当前位置变化时重建有限预取队列；持续维护待加载集合。可见页最高优先，其次邻近页。避免每完成一个文件就重算全书，也不必只为了填满 512 MiB 而预读远处媒体。

### 4. 高优先级：播放命令会竞争持有等待操作的锁

位置：`MpvVideoPlayerControl.xaml.cs:474`、`:571`、`:584`。

事件线程在 `_mpvLock` 内执行 `WaitEvent(_mpv, 0.1)`；UI 发起的暂停、恢复、停止、加载也使用同一把锁。因此命令可能等待一次最长 100 ms 的事件等待周期，连续竞争时还可能更久。当前调用结构已确认，实际输入延迟尚未测量。

建议：用专用事件/命令所有者管理原生句柄，等待事件期间不占用 UI 命令所需的互斥锁；关停时先停止事件读取，再安全销毁句柄。修改时同时核对原生事件数据的有效期，不能只把 lock 删掉。

### 5. 中高优先级：任务取消后没有完整等待工作结束

位置：`MainWindow.Media.cs:32`、`:51`、`:60`、`:67`、`:444`。

加载循环使用 `using var parallelGate`。如果等待配额时发生取消，会跳过正常路径中的 `Task.WhenAll(workers)`，随后释放信号量；已经运行的 worker 仍可能在 finally 中调用 `parallelGate.Release()`。另有已完成 worker 被直接移出列表的路径，使后台异常不易被观察。

建议：采用固定数量 worker 或一个明确拥有全部任务的加载器；停止流程遵循“取消 → 等待 worker 完成 → 释放配额和会话”。对已登记但未开始运行的请求也保证一次且仅一次的清理。该风险来自控制流分析，尚未做并发压力复现。

### 6. 中优先级：图片加载与界面更新存在可避免的重复工作

位置：`MainWindow.Media.cs:237`、`:499`、`:543`、`:559`、`:632`；`MainWindow.Navigation.cs:18`、`:71`、`:351`。

- 图片宽高读取发生在 `AcceptImage` 的 UI 回调中；应在读取/解码任务中得到元数据后统一提交结果。
- 每次图片接收、滚动都会取消并重建 50 ms 解码延迟。素材持续快速到达时，可见图片可能要等加载安静下来才开始解码。
- 解码任务只有按文件名去重，没有独立并发上限；快速跳页时，旧页解码仍可继续执行。
- 每次滚动都扫描全书统计已加载区间，并扫描全书查找要清理的位图。
- 每次窗口宽度变化都会调整全部页面并通知属性；只要解码宽度稍有增长，就先清空现有图像再重解码。
- 解码异常被静默吞掉，没有明确失败状态；坏图在后续调度中可能反复尝试。

建议：可见页立即进入有界解码队列，预取页使用延迟调度；缓存图片元数据，维护已解码页面集合与加载统计；宽度变动做合并和档位控制，在新位图准备好前保留旧图；统一错误状态与重试策略。

### 7. 中优先级：上层并行读取没有带来并行解压

位置：`ArchiveSession.cs:57`、`:64`、`:68`、`:92`；`MainWindow.xaml.cs:13`。

上层有两个加载 worker，但一个 ArchiveSession 的整个查找、打开和复制过程都在同一个信号量内执行。实际同一时间只有一个条目在解压。另外每次按名称线性查找条目，每次复制新分配 128 KiB 缓冲区。

建议：保留归档读取的安全串行边界，后台读取与图片解码形成流水线；为条目建立索引，明确同名条目的处理规则；复用复制缓冲区。不要直接删除归档锁，也不要未经格式测试就增加多个归档实例。不同 ZIP/RAR、solid RAR 的访问成本仍需真实素材验证。

### 8. 中低优先级：视频封面存在编码后再解码的链路

位置：`VideoThumbnailService.cs:456`；`MainWindow.Video.cs:445`；`MainWindow.Media.cs:615`。

当前是 mpv 原始截图 → 托管像素 → BitmapSource → PNG 编码 → byte[] → BitmapImage 解码。对纯内存的当前显示而言，这里有额外 CPU 和复制开销，但 PNG 也有节省缓存空间的价值。

建议：优先让当前可见封面直接使用冻结后的位图；需要保留较多封面时再评估编码缓存。记录封面生成耗时和实际内存，决定是否删除编码路径，避免仅凭代码长度取舍。

## 可精简的结构与代码

| 当前情况 | 建议 | 预期收益 |
| --- | --- | --- |
| MainWindow 用 partial 分文件，但共享几十个字段 | 建立 ReaderSession，集中会话身份、缓存和任务生命周期；窗口保留输入与视觉处理 | 减少跨文件状态依赖，容易验证切包与关停 |
| ComicPage 同时持有数据、位图和 WPF 播放器，且能 Pause/Stop | 收敛为页面显示状态；播放器由 PlaybackController 管理 | 明确媒体资源所有者，减少重复控制入口 |
| 控件、引擎、OpenGL 和原生定义都在一个文件 | 按原有类型分别归位，原生定义统一放 Interop | 改动边界清晰；单纯搬文件本身不算性能提升 |
| VideoThumbnailService 只有转发，provider 当前只有一种实现 | 合并多余转发层；若有测试替身需求，仅保留一个小接口 | 降低间接调用与维护层数，主要是代码简化 |
| 原生播放事件先切到 UI，MainWindow 又 BeginInvoke | 在统一事件入口完成一次 UI 调度，并关联会话/媒体身份 | 减少队列往返和旧媒体事件污染新状态的风险 |
| XAML 约前 500 行主要是资源、样式、模板 | 将可复用样式移入少量 ResourceDictionary，页面模板单独整理 | 窗口结构容易阅读，非主要性能优化 |
| 若干旧入口已无项目调用 | 删除前确认外部用途，再连同内部辅助链路清理 | 直接减少无效维护面积 |

已确认在仓库内没有有效业务调用的候选包括：播放器的 `SourceBytes` 依赖属性入口、`PrepareFirstFrame`、`PlayAsync` 重载、`CaptureCurrentFrame` 调用链，以及 `ComicPage.ResumeVideo/StopVideo`。`ClearMediaCache(bool clearPages)` 仅以 false 调用，可以取消未使用分支。`VideoCoverGeneratorHost` 当前实际承担共享播放器待机容器，名称与用途已经不符；需要判断其初始化作用后再改造，不能直接按“旧封面代码”删除。

另外，当前没有测试项目、基准工程或 README。项目依赖本机已有的 `Native/win-x64/libmpv-2.dll`，但该文件被 .gitignore 排除，仓库中没有获取与校验脚本。当前构建成功不代表新环境可以复现构建。项目还在所有配置中禁用调试符号，不利于后续定位源代码层面的性能问题。

## 应保留的基础

- `VirtualizingStackPanel`、Recycling 和像素滚动已经配置，应先验证实际行为，再调整缓存长度。
- 图片已按显示宽度与 DPI 解码，后台生成后 Freeze，且仅保留可见区域及邻页的解码图。
- 播放器实例共享和 headless 封面实例复用的方向合理。
- 已尽量使用 ArraySegment 复用读取缓冲区，避免对完整视频额外 ToArray。
- 归档访问封装在 ArchiveSession，媒体分类和自然排序已有独立小类。

这些基础说明重构可以逐块替换，不需要同时更换 UI 框架、解压库和播放器。

## 建议的实施顺序

### 第一阶段：建立基线并修正资源与任务生命周期

记录首屏、跳页、滚动、内存、切包和关停行为；补充少量针对边界的测试。修复旧任务清理新状态、预算准入、重复媒体加载、视频源释放及取消后的任务收尾。

验收重点：旧会话结果不能修改当前会话；同一条目在会话内只有一个有效读取请求；取消后计数归零；停止视频和切包后，托管媒体缓冲不再被长期服务保留。通过对象引用和进程内存同时判断，不能要求工作集立即下降来证明释放。

### 第二阶段：减少热点工作量

替换全书反复排序，建立可见页优先的有限预取；索引归档条目，复用复制缓冲；把元数据读取移出 UI；限制解码并发；减少全书扫描、重复 UI 调度和缩放重解码。

验收重点：页数增长不再导致每个加载请求都重新排序全书；预读远处内容不会持续推迟首屏；滚动和窗口缩放的 UI 线程占用降低；所有比较使用相同素材、DPI、窗口大小和缓存条件。

### 第三阶段：收敛模块和删除遗留代码

在行为稳定后提取 ReaderSession、MediaLoadScheduler、ImageDecoder、PlaybackController 和 PasswordStore 等少量具体模块；缓存先作为会话内部部件，复杂到需要独立验证时再提取。保留现有 ArchiveSession 与原生互操作封装。清理未用入口、重复状态以及多余包装层，整理 XAML 资源。

第一轮继续使用一个应用项目即可；只有确有无 UI 测试或复用需要时，再建立独立核心类库。

### 第四阶段：按实测决定视频深层优化

处理 mpv 事件/命令竞争和原生句柄生命周期；评估封面的位图/编码缓存取舍，验证 GPU 帧更新与播放器宿主切换。大视频存储方式单独决策。

## 基准素材和回归场景

| 场景 | 重点指标或行为 |
| --- | --- |
| 小型纯图片 ZIP | 打开到首张图、普通滚动是否回退 |
| 2,000–5,000 页图片包 | 加载调度 CPU、累计分配、跳转末页耗时 |
| 高分辨率或长条图片 | 解码时间、解码内存峰值、缩放时是否闪白 |
| ZIP/RAR、加密包、solid RAR 样本 | 自然排序、密码流程、随机读取、取消响应 |
| 图片视频混排及接近预算上限的视频 | 点击到首帧、预加载去重、封面耗时、内存持有 |
| A/B 两个包包含相同文件名，连续快速切换 | generation 隔离、旧事件、预算与加载标记 |
| 加载、解码、封面生成期间关闭窗口 | worker 收尾、句柄释放、是否卡住或留下后台异常 |
| 坏图、坏视频、损坏压缩包 | 明确错误状态、有限重试、后续页面仍可操作 |
| 暂停/恢复、连续播放不同视频、窗口缩放 | 输入延迟、旧媒体事件、首帧与渲染资源生命周期 |

建议记录：首屏和跳页延迟、UI 线程耗时/卡顿分布、总分配和 GC 次数、托管堆与进程 Private Bytes 峰值、解压/解码/封面各阶段耗时、切包后仍被引用的媒体数组。完成基线后再制定可量化的性能目标。
